# Mission Core pilot status — 20 October 2026

Mission Core is an unsigned Windows desktop pilot, not a production security release. The native app builds and opens. The browser at http://127.0.0.1:1420 is a temporary design preview and cannot use a USB vault.

Implemented: empty device-owned encrypted vault; no Mission account; globe identity, Handjet, cream/blue-haze interface; five-step reviewed onboarding; text/Markdown/JSON imports; human memory editor and history; default-deny per-agent grants; read-only MCP search/get with separate agent credentials; setup formats for Claude Desktop, Codex, Cursor, Gemini CLI, GitHub Copilot in VS Code and generic stdio clients. Security now includes a passphrase-confirmed USB vault reset that revokes the current session, deletes Mission files only, and returns to onboarding after a new vault is created.

Hosted AI pilot: Requesty key entered after USB unlock in the AI page, held in native session memory, cleared on lock or detected disconnect. The app retrieves a model catalogue or accepts a Requesty model/policy ID. Each request requires a question, explicit memory selection, payload review and consent. Responses stay temporary unless opened as a memory draft and manually saved. The Requesty key is not saved to the USB, app settings or Git. The selected context and question leave the device when Ask is pressed. Model listing does not prove a given key can use each listed model.

Verified locally: production frontend build; 28 TypeScript tests; 10 Playwright browser flows; 13 focused Rust cryptography/core tests; updated native desktop build. The previous revision passed 28 full Rust native tests and a Node MCP adapter integration test; the full Rust suite was not rerun for this diagnostic update. The browser checks simulate a returning vault under a new drive letter, reset confirmation and fresh onboarding. The current USB's vault files were detected, and its signed header verified without reading personal memory. Desktop key-entry and Requesty response paths have not been exercised with a real key because none was supplied. Browser simulation cannot prove native USB and hosted API behaviour.

Remaining pilot gates: retry physical USB unlock with the new category-specific error feedback, then reset and recreate only on a disposable pilot vault; live Requesty call, live agent interoperability, OS write tracing and recovery. The user reported successful context revocation on removal in the first pilot. This revision found an existing USB vault with a valid signed header; the app was unable to distinguish passphrase, storage and post-unlock snapshot failures in its previous generic message. No reset was performed. Email, calendar, camera and health connectors, local laptop AI, signed installer and updates remain unfinished.

Security limitations: SQLCipher reported VirtualLock error 1453, so locked RAM and absence of pagefile copies cannot be claimed. The GNU development build emitted a multiple-manifests linker warning. A lease check is not proof of the physical one-second unplug target. Vault reset deletes files but is not a guaranteed secure erase of flash storage. Already transmitted content can remain with a model provider or agent.

See PILOT.md and SECURITY.md. No API key, seed memory, real account connection or compiled binary is committed.
